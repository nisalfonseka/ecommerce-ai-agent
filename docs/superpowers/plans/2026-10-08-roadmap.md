# ACE Delivery Roadmap

> Implements the [design spec](../specs/2026-10-08-ai-commerce-engine-design.md). Runtime behaviour is described in
> [`docs/workflow.md`](../../workflow.md). Each phase gets its own detailed TDD plan (`docs/superpowers/plans/`) when it
> starts. Phase 1's plan is already written: [2026-10-08-phase-1-foundation.md](2026-10-08-phase-1-foundation.md).

**Rule:** do not start a phase until the previous phase's exit criteria are met and its open decisions are answered.

| Phase | Name | Outcome | Depends on | Decisions needed |
|---|---|---|---|---|
| 0 | Setup | Accounts, repo, keys, VPS | — | — |
| 1 | Foundation | Monorepo + commerce contract + conformance suite + memory adapter | 0 | — |
| 2 | Agent core | Agent that sells against the memory adapter, with evals | 1 | D3 |
| 3 | Engine API + persistence | Multi-tenant HTTP API, Postgres, streaming, limits, tracing, VPS staging | 2 | — |
| 4 | Chat widget | Embeddable widget with cards, cart sync, actions | 3 | — |
| 5 | Reference store + first real adapter | Medusa store, PayHere + COD, `adapter-medusa`, attribution | 1, 4 | D1, D4 |
| 6 | Search, sync and knowledge | Read model, enrichment, hybrid search, RAG, webhooks, reconciliation | 5 | — |
| 7 | Support, identity, handoff, privacy | OTP, order lookup, handoff inbox, PDPA features | 6 | — |

## Phase 0 — Setup (owner, ~1–2 days, no code)

- Product name (D5) is not final; `ACE` / `@ace/*` is the working placeholder.
- Create a GitHub repository; enable branch protection on `main`.
- Install Node 24 LTS, pnpm (via corepack), and Docker (for local Postgres later).
- Create API keys for **Google AI (Gemini), OpenAI and Anthropic**; set spend limits on each.
- Start applications that take time: **PayHere merchant (sandbox) account** and **Meta Business verification** (needed
  for WhatsApp in Phase 10).
- Before Phase 3: provision the **VPS** (Ubuntu LTS, Docker + Compose, SSH key login only, firewall, unattended security
  updates), a domain with DNS, and an off-site backup target for Postgres.
- Read `AGENTS.md`.

**Exit:** repo exists, toolchain installed, accounts requested.

## Phase 1 — Foundation (detailed plan ready)

Monorepo (pnpm + Turborepo + TypeScript + Biome + Vitest), `@ace/contracts` (Money, errors, catalog/inventory/cart/
checkout/order/identity schemas, capabilities, `CommerceProvider`), the `describeProviderConformance` suite, and
`@ace/adapter-memory` with a seeded clothing catalog that passes it.

**Exit:** `pnpm lint && pnpm typecheck && pnpm test` green; memory adapter passes 100% of the conformance suite;
ADR-001 (commerce contract) written.

## Phase 2 — Agent core

- Contract v1.1 (additive): `updateCartAttributes(cartId, attributes, opts)` under `cart.write`, so ACE can tag the host
  site's existing cart with `ace_conversation_id` (spec G2 + G14); memory adapter + conformance test.
- `@ace/agent`: `ToolContext`, tool definitions (Zod input schemas, typed UI-part outputs), session state with
  result references (`#1…#n`), prompt composer (safety core + persona + store facts), guardrails (grounding validator,
  quantity rules, topic boundary), `ToolLoopAgent` wiring, conversation summarisation.
- Tool registry built from adapter capabilities + tenant config.
- `@ace/evals`: golden conversation format, scorers (tool-call match, grounding, language, refusal), CLI runner,
  30+ cases across English / Sinhala / Tamil / Singlish, including prompt-injection cases hidden in product
  descriptions.
- Deterministic agent tests with a mock language model.
- Run language and tool-use evals on **Gemini, OpenAI and Claude** candidates (conversation model + cheap model each),
  then compare quality, Sinhala/Tamil/Singlish handling, latency and cost per conversation → answer **D3**.

**Exit:** ≥ 90% eval pass; 0 safety failures; ordinal references ("the second one in large") resolved correctly in
all cases; no price in text that is not in tool output.

**Status (2026-10-09):** built. D3 is answered by running `pnpm evals` with keys for all three providers and reviewing
`evals-reports/*.md` (pass rate per language, Sinhala/Tamil transcripts, tokens, latency).

## Phase 3 — Engine API and persistence

Detailed plan (draft): [2026-10-09-phase-3-engine.md](2026-10-09-phase-3-engine.md). Owner decisions E1 (reply delivery) and
E2 (model prices and budgets) are listed there.

- Idempotency layer per ADR-002 (`IdempotentCommerceProvider`, Postgres `idempotency_records`, fingerprint → CONFLICT,
  ambiguous-failure reconciliation); conformance replay test runs against wrapped adapters.
- `@ace/db`: Drizzle schema for the tables in spec §4.5, migrations, RLS policies, `withTenant()`, envelope
  encryption for store credentials.
- `apps/engine` (Hono): `POST /v1/chat` (SSE stream), `POST /v1/actions/:type`, `GET /v1/conversations/:id`, widget-key
  auth + origin allow-list, rate limiting, budget checks, usage ledger, tracing (OpenTelemetry), PII redaction.
- Tenant/store/bot admin endpoints (internal, API-key protected) and a seed script for a demo tenant on the memory
  adapter.
- Integration tests against real Postgres (Docker).
- Deployment: Dockerfiles for `engine` and `worker`, a `docker-compose.yml` (engine, worker, postgres + pgvector, Caddy
  for TLS), a GitHub Actions deploy over SSH, nightly `pg_dump` to off-site storage, and health checks + uptime
  alerts. Deploy a staging environment on the VPS.

**Exit:** two demo tenants with isolated data (RLS test proves tenant A cannot read B); chat streams end-to-end on
staging; cost per conversation visible.

## Phase 4 — Chat widget

- `@ace/widget`: single script, Shadow DOM, launcher + panel, streaming text, product/cart/checkout/order cards,
  card buttons → `/v1/actions`, consent notice, accessibility (keyboard, screen reader), mobile layout, Sinhala/Tamil
  font support.
- Host integration API: `data-key`, `ACE.setCart(cartId)`, `ACE.setIdentity(token)`, `ace:cart-updated` event.
- Demo host page.

**Exit:** on a plain HTML demo page, a shopper finds, adds and checks out (memory adapter) using chat and buttons; the
cart badge updates; the bundle is < 60 kB gzipped.

## Phase 5 — Reference store and first real adapter

- Entry gate — extend the conformance suite before the first real adapter: replay for createCart/updateCartLine/createCheckout,
  failed-write retry, atomicity with a pre-existing line, over-stock requests, fixture self-checks, getInventory omits
  unknown IDs, listOrders newest-first, createCheckout OUT_OF_STOCK, updatedSince inclusive, ProductSchema cross-field
  checks (variant.productId, priceRange), datetime normalised to Z, `CommerceError` gains `cause` and a brand check.
- Answer **D1** and **D4**.
- `apps/reference-store`: Medusa v2 backend (region LKR, clothing product types, sizes), Next.js storefront, PayHere
  payment provider (hash verification on `notify_url`), COD payment method, cart attribute passthrough, order webhooks.
- `@ace/adapter-medusa`: implements the contract and passes conformance against a local Medusa instance.
- Contract v1.1: `orders.place_cod` capability (`placeCodOrder`) and the confirmation flow (spec G5,
  workflow §E).
- Widget installed on the storefront with real cart sync.

**Exit:** on staging, a shopper completes a PayHere sandbox payment and a COD order through chat; the order carries
`ace_conversation_id`.

## Phase 6 — Search, sync and knowledge

- `apps/worker` with pg-boss: `sync.product`, `sync.reconcile`, `enrich.product`, `embed.product`,
  `knowledge.ingest`, `retention.purge`.
- Webhook ingress: signature verification, `webhook_events` dedupe.
- `@ace/search`: read model, enrichment (cheap model + merchant overrides), query normalisation, FTS + pgvector + RRF,
  filters, business rules, live re-check, `IndexedCatalogProvider` decorator.
- `@ace/knowledge`: ingestion (markdown, PDF, URL), chunking, embeddings, retrieval with threshold + citations;
  `search_knowledge` tool.
- Search relevance eval set (50 queries with expected products, including Singlish).

**Exit:** search eval nDCG@5 ≥ target agreed in the phase plan; a price change on the store is visible to the agent
within 60 s; reconciliation repairs a deliberately dropped webhook.

## Phase 7 — Support, identity, handoff, privacy

- Tie `identityMatches` to `method` (email_otp → email only, phone_otp → phone only, host_session →
  externalCustomerId + host-verified fields) with negative tests.
- Identity: signed host-session tokens; email/phone OTP (`start_verification`), rate-limited.
- `lookup_order` / `list_orders` tools wired to the contract.
- Handoff: `request_human`, automatic triggers, minimal `apps/dashboard` inbox (Next.js) with take-over / hand-back,
  staff notifications.
- PDPA features: consent records, retention purge, export/delete API, DPA template, breach runbook, provider
  data-retention settings verified.

**Exit:** evals for order support and handoff pass; an order cannot be read without verification (security test);
deletion request removes all shopper data for a tenant.

## Phase 8 — Pilot launch

- Run the onboarding runbook (workflow §A) for the first client.
- Dashboards: KPIs from spec §4.7; alerts on error rate, latency and budget.
- Two-week soft launch → public launch → weekly improvement loop (workflow §L).
- Answer **D6** (pricing) using measured cost per conversation.

**Exit:** 4 weeks live; KPIs reported to the client; no P1 incidents open.

## Phase 9 — Second platform (proves the architecture)

- `@ace/adapter-shopify`: catalog through Shopify's UCP catalog tools (`search_catalog`, `lookup_catalog`,
  `get_product`), carts and checkout handoff (`continue_url`), Admin API webhooks for sync, and order lookup through the
  Admin API with the identity check. **Check the live `tools/list` first**: Shopify renamed tools during the UCP
  migration.
- Passes conformance against a Shopify development store.
- Onboard a Shopify tenant with **no changes to `@ace/agent`** (enforced: the phase PR must not touch
  `packages/agent`).

## Phase 10 — WhatsApp channel

- `Channel` interface; WhatsApp Cloud API adapter (webhooks, 24-hour window, templates, opt-in records).
- Cards rendered as WhatsApp interactive messages (lists/buttons) and checkout links.
- Per-message cost metering in the usage ledger (per-message billing since Oct 2026).
